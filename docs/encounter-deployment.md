This client is a synthetic backend test identity, not a human prescriber login or external prescribing authorization.

Policy is declarative and generated by `make encounter-prepare` from the two scenario identities and verified reference context. It permits:

- Exact two Encounters: read/search/create/update plus history/vread for version evidence.
- Exact two MedicationRequests and two Tasks: read/search/create; no update/delete. MedicationRequests must be draft/proposal, Tasks draft/plan.
- Read/search only for the two existing patients, one caregiver, two role references, two visit locations and Helix organization. No Patient, RelatedPerson or foundation writes.
- Encounter FHIRPath constraints: creation planned only, sequential status progress or cancellation, no terminal reopening, immutable patient reference. Other Encounter fields are not a complete server field allowlist; the supplied runtime command changes status only. No broad clinical/admin or proxy grant.

Constraints were evaluated with the Medplum FHIRPath implementation and policy/resource payloads validated without persistence. Server enforcement still requires the live acceptance below.

## Bootstrap plan, deploy and verify

`make encounter-plan` from code/ authenticates only the new encounter client, checks project/effective policy including write constraints, verifies live group/role/site/caregiver references and current routing eligibility, validates the six payloads, rejects duplicate identities and snapshots the managed resources. It saves hashes/versions/identifiers only, not resource bodies, under ignored reports/encounters/plan.json. Expected first plan: **six creates, zero updates/deletes**.

After reviewing the plan and receiving owner authorization, `make encounter-deploy` conditionally creates the six cross-linked resources in one transaction and independently verifies the result. Existing resources resolve by identifier; no search-then-create. Repeating PLAN must retain all six, and an unchanged reviewed retain plan applies zero writes. Changed references, tags or other managed fields block writes.

The encounters.yml workflow provides equivalent PLAN/DEPLOY using only encounter secrets, existing shared staging concurrency and owner approval. DEPLOY consumes the successful same-main-commit PLAN artifact, requires provenance from this workflow, and rejects expired/changed plans. Dispatch PLAN, let owner approve validation, review result, obtain explicit dispatch authorization for DEPLOY, then let owner approve writes. Never use local artifacts in the hosted workflow.

## Separate encounter lifecycle acceptance

After bootstrap verification, `make encounter-flow-plan` saves a separate snapshot/configuration/commit-bound plan for **four successful Encounter updates**: planned → in-progress → finished for each visit. It makes no writes. Both visits must still be planned.

After owner review/authorization, `make encounter-flow-apply` runs the approved sequence. It checks server rejection of skip-to-finished, stale If-Match writes and terminal reopening, then confirms version history contains planned/in-progress/finished for each visit. Those expected-denied requests are not additional successful writes. No MedicationRequest or Task update is attempted; proposals stay draft. No prescription is signed or transmitted.

The flow runner is local, not part of the bootstrap GitHub workflow. It uses the same scoped encounter client and does not need additional secrets. A flow plan expires after 24 hours and binds current snapshots; config/commit/version changes require replanning. Finished encounters are retained and never reset to planned by bootstrap. The lifecycle test is not replayable on those finished visits; add an explicitly reviewed new scenario identity for another episode instead of overwriting history. If interrupted, inspect state and prepare reviewed recovery; there is no automatic rollback or reset. An assertion failure may occur after a successful write, so do not assume failure means nothing changed.

`make encounter-verify` requires all six correct cross-linked resources and preserves legitimate runtime Encounter status. It rejects unexpected tags, content or reference changes; it is not a reset operation. `make encounter-access` uses existing enrollment and clinical acceptance identities to verify that direct reads/searches of the six known existing encounter resources are denied/filtered despite patient visibility. It makes no writes. Existing caregiver grants are demographic-only and do not enable these resources.
